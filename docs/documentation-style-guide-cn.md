# Wirelink 人类优先文档写作与教程设计指南

本文规定 Wirelink 面向使用者的文档应如何组织、写作和评审。它借鉴 Astro 文档的语言规范与教程结构，并结合 Wirelink 当前的概念、示例和文档目录给出可执行的改造方法。

这是一份文档建设规范，不定义协议或 API 行为。涉及技术事实时，以 Wirelink 的协议、API 和源码为准。

## 目标

Wirelink 文档首先服务正在完成任务的人。读者不应先理解整个系统，才能运行第一个例子；也不应为了理解一个新术语，在多个页面之间来回猜测。

一篇合格的入门或教程文档应让读者清楚回答这些问题：

- 这篇文档适合谁？
- 开始前需要会什么、准备什么？
- 完成后能做什么？
- 当前步骤为什么存在？
- 运行后应该看到什么？
- 新出现的概念是什么意思，在哪里可以继续阅读？
- 下一篇文档是什么，为什么现在该读它？

文档首页、教程、操作指南、概念说明和参考手册承担不同职责。不要让一篇页面同时承担所有职责。

## 从 Astro 学到什么

Astro 的文档规范和教程采用同一套思路：降低读者在每一步需要同时处理的信息量，让概念在真实需求出现时进入视野。

### 语言清楚、直接、克制

Astro 的写作规范强调短句、短段落、常用词和较少的前置假设。Wirelink 应采用同样的原则：

- 先说读者要执行的动作，再说明原因。
- 使用主动语态，明确动作由谁完成。
- 一个句子只承担一个主要意思。
- 一个段落围绕一个问题展开。
- 使用平静、友好、尊重的语气，避免过度随意或夸张。
- 用事实描述行为。不要用口号替代边界和结果。
- 直接使用“你”称呼读者；通常省略“我们将”“让我们”“笔者认为”。
- 指令使用明确的祈使句，例如“运行”“添加”“检查”。
- 必须执行的步骤不要写成“可以”“应该”“不妨”。
- 不要用“显然”“很简单”“只需”“众所周知”。这些词不会帮助遇到困难的读者。

标题也应说明读者要完成的动作或得到的结果：

- 推荐：`发送第一条温度消息`
- 推荐：`让 RPC 失败变得可观察`
- 避免：`关于消息的一些说明`
- 避免：`进阶内容`

### 从具体任务进入概念

Astro 的教程围绕一个持续演进的博客项目展开。每一课先利用上一课已经完成的成果，再引入当前遇到的新需求。Wirelink 教程也应围绕同一个可运行示例逐步扩展，而不是每篇重新展示一套互不相干的 API。

推荐的递进顺序是：

1. 先运行一个能工作的基线。
2. 提出一个读者现在能理解的具体需求。
3. 只修改实现该需求所需的代码。
4. 立即运行并观察结果。
5. 根据刚刚观察到的行为解释新概念。
6. 让读者独立完成一个小变化。
7. 用知识检查确认读者能把概念用于新情境。
8. 用能力清单收束，并引向下一篇。

这种顺序把抽象名词放在经验之后。读者先看到问题和行为，再得到准确术语。

### 每课只有一个主要概念轴

教程的一课可以涉及多个 API，但只能要求读者建立一个主要的新心智模型。例如：

- “最新值”一课讨论新值如何覆盖旧值。
- RPC 一课讨论请求如何获得业务结果。
- 所有权一课讨论数据可以安全使用到什么时候。
- 集成一课讨论谁推进端点、数据如何进入和离开 Wirelink。

如果一篇页面同时首次引入 codec、runtime、binding profile、session identity、adapter、envelope、owner 和 diagnostics，读者无法判断哪些是当前必须理解的内容。应拆分页面，或把非必要概念移动到后续概念说明和参考手册。

### 支架逐步减少

Astro 的早期课程提供具体文件、完整操作和预期结果；后期课程逐渐改为挑战，并把提示与答案折叠起来。Wirelink 可以采用相同节奏：

- 入门阶段提供可复制的命令、文件位置、最小完整代码和预期输出。
- 中间阶段提供局部 diff，并要求读者解释结果。
- 进阶阶段先给目标和约束，再提供提示与参考实现。

减少支架必须发生在读者已经练习过相同类型任务之后。不要在首次出现概念时用“请自行实现”代替教学。

### 每一步都有可观察结果

Astro 教程频繁要求读者查看浏览器结果。Wirelink 没有浏览器界面，但同样需要明确反馈：

- 进程输出了哪一行日志？
- 回调是否被调用？
- 哪个计数器发生变化？
- 当前返回码是什么？
- 队列满、超时或断线时会看到什么？

“构建成功”通常不足以证明读者理解了行为。优先选择能体现本课概念的观察点。

### 通过对比和暂时失败建立理解

Astro 会让读者比较修改前后的页面，或者先观察缺少某个步骤时的结果。Wirelink 也可以安全地制造小型对比：

- 先连续发布多个值，再观察订阅者只读到最新值。
- 先不推进 endpoint，再观察 RPC 不会自行完成。
- 先保留 borrowed view，再在下一次推进前后比较其有效期。
- 先触发超时，再添加正确的推进循环并观察成功。

这类练习必须可恢复，并清楚写出预期现象和恢复步骤。

### 代码示例承担教学任务

Astro 要求代码示例来自真实、可工作的场景，并在代码块之前说明它展示什么、放在哪里以及为什么需要它。Wirelink 的代码示例应遵守以下规则：

- 使用真实示例名，例如 `temperature_centi_c`，不要使用 `foo`、`bar`。
- 在代码块上方标出文件路径。
- 在命令上方说明工作目录。
- 在代码前解释这次修改的目标。
- 在代码后立刻给出预期输出或状态变化。
- 修改已有文件时优先展示 diff 或高亮行。
- 只展示完成当前任务所需的配置；完整选项放进参考手册。
- 连续出现多个代码块时，分别在每个代码块之前解释，不要先堆放代码再统一说明。
- 教程中的代码应来自可构建示例，或由 CI 验证，避免复制后逐渐失真。

### 检查应用能力，而非名词记忆

Astro 教程在每课末尾使用选择题和能力清单。选择题最有价值的用途是检查读者能否预测行为或选择方案。

推荐的问题：

> 发布者连续写入 21.00°C、21.10°C 和 21.20°C，订阅者只在最后推进一次。使用 latest 语义时，它应读取哪个值？

不推荐的问题：

> `wl_sub_latest_read()` 函数叫什么？

每课设置 1 至 3 题即可。错误选项应代表常见误解，反馈要解释原因。题目不计分，也不阻断后续阅读。

能力清单使用读者可以验证的陈述：

- 我能发送并读取一个 latest 值。
- 我能解释 latest 与 reliable 的区别。
- 我能根据返回码判断本次 RPC 是否已获得业务结果。

不要写成“我已经阅读本章”或“我了解 Wirelink”。

## Wirelink 的目标信息架构

公开文档应明确分为五类。页面标题、导航位置和开头说明都要让读者知道自己正在阅读哪一类。

| 类型 | 回答的问题 | 写作方式 | Wirelink 中的例子 |
| --- | --- | --- | --- |
| 教程 | 我怎样从零建立理解？ | 连续场景、固定顺序、小步练习 | 入门、RPC、所有权、异步执行 |
| 操作指南 | 我怎样完成一个明确任务？ | 假定基础知识，直接给步骤和决策点 | 接入 UART、配置时钟、排查超时 |
| 概念说明 | 为什么系统这样工作？ | 建立心智模型，比较相近概念 | 投递与业务完成、owner、session identity |
| 参考手册 | 某个接口或格式的精确定义是什么？ | 完整、稳定、便于查找 | API、schema、协议、返回码 |
| 维护者资料 | 项目怎样演进和验证？ | 面向贡献者，保留证据与历史 | benchmark、审计记录、发布检查 |

参考手册可以密集，但开头仍需写明目标读者、前置知识和相关教程。教程则必须在自己的教学范围内自洽；读者不应为了完成当前步骤，被迫先读完整参考手册。

建议逐步形成以下目录。迁移时应保留重定向或同步修复仓库内链接：

```text
docs/
  learn/
  how-to/
  concepts/
  reference/
  maintainers/
```

### README 的职责

README 是入口，不是整套参考手册。它的前半部分应按以下顺序回答问题：

1. Wirelink 帮谁解决什么问题。
2. 一个最小、具体的使用场景。
3. 如何运行第一个示例。
4. 读者接下来应选择哪条学习路径。
5. Wirelink 的关键边界和适用范围。
6. 安装、兼容性、支持和贡献入口。

详细的 benchmark 历史、内部强化进度、完整协议细节和所有配置项应进入对应的参考或维护者页面，再由 README 使用描述性链接指向它们。

当前 README 首段一次引入 allocation-free、framing、CRC、stop-and-wait、borrowed RX、SPSC/DMA ingress、hardware、threads、heap 和 clock。它准确，但要求新读者在理解用途之前建立过多概念。

可以改为两层表达：

> Wirelink 帮助两个嵌入式或桌面端点通过点对点链路交换类型明确的消息。它提供消息成帧、完整性检查、可选的可靠投递和应用层辅助，同时让应用继续掌控存储与执行。
>
> 如果你第一次使用 Wirelink，请先运行“让显示端读到最新温度”。完成后，再根据需求学习 RPC、数据所有权或硬件接入。

第一层让读者判断产品是否相关，第二层给出行动。allocation-free 等关键特性仍应保留，但可以放在紧随其后的能力列表中逐项解释。

## 推荐的教程递进

现有温度示例适合作为贯穿教程的项目。后续课程继续扩展这个系统，让读者复用已经熟悉的 schema、构建命令和两个端点。

| 阶段 | 读者要完成的任务 | 本课允许首次引入的主要概念 | 本课暂缓的内容 |
| --- | --- | --- | --- |
| 1. 最新温度 | 发布温度，显示端读取最新值 | endpoint、message、schema、latest | frame、CRC、DMA、session identity |
| 2. 请求校准 | 发起一次校准 RPC 并读取结果 | request/response、可靠投递、业务完成、超时 | RPC 缓存内部结构、异步句柄 |
| 3. 保存返回值 | 在下一次推进后继续使用 RPC 结果 | borrowed view、owned value、生命周期 | allocator 设计、所有底层存储槽 |
| 4. 延后处理 | 把耗时校准工作交给应用执行 | owner、async/deferred、完成与取消 | 具体 RTOS 集成细节 |
| 5. 接入真实链路 | 将相同应用连接到 UART、TCP 或自定义传输 | adapter、envelope、clock、推进循环 | 完整 wire format |
| 6. 处理重连与故障 | 观察超时、重试、重连和诊断 | session identity、诊断计数器、恢复策略 | 协议字段逐字节说明 |

这是概念预算，不是 API 预算。一课可以调用若干函数，但读者只应被要求建立一个新的主要关系。

## 新概念的引入规则

任何对完成当前任务必需的新概念，在第一次出现时必须满足以下一种条件：

1. 在同一段中用常用语言解释，并立即给出例子；或
2. 明确列为前置知识，并链接到已经完成教学的页面。

非必要概念可以链接到延伸阅读，但不能让它打断当前步骤。

### 推荐的解释顺序

使用以下顺序介绍 Wirelink 概念：

1. **熟悉的问题**：读者当前遇到了什么现象或需求。
2. **普通语言解释**：系统需要建立什么关系。
3. **正式术语**：给出 Wirelink 使用的名称和 API 标识符。
4. **具体例子**：展示输入、动作和结果。
5. **边界**：说明它保证什么，以及不保证什么。
6. **深入链接**：指向概念说明或参考手册。

例如，不要直接写：

> 配置 session identity，并选择合适的 envelope adapter。

可以写成：

> 端点重连后，需要区分新会话和断线前遗留的数据。Wirelink 使用 **session identity（会话身份）** 完成这项区分。先为每次连接提供新的会话标识，再把收到的数据交给 endpoint。参见[会话与重连](./session-cn.md)。

如果目标页面尚不存在，先在当前页面提供完成任务所需的最小解释，并创建明确的文档待办。不要留下只有术语、没有定义的链接占位。

### 术语应保持稳定

首次出现时使用“中文说明 + 英文正式名称或 API 标识符”，此后固定使用同一个称呼。不要为了文采轮换近义词。

| 正式名称 | 首次出现时的推荐写法 | 后续写法 |
| --- | --- | --- |
| endpoint | endpoint（通信端点） | endpoint |
| schema | schema（消息定义） | schema |
| binding profile | binding profile（消息使用配置） | binding profile |
| reliable delivery | reliable delivery（可靠链路投递） | 可靠投递 |
| RPC completion | RPC 业务完成 | 业务完成 |
| borrowed view | borrowed view（借用视图） | borrowed view |
| owned value | owned value（自持值） | owned value |
| owner | 推进 endpoint 的唯一 owner | owner |
| adapter | adapter（传输适配器） | adapter |
| envelope | envelope（链路封装方式） | envelope |
| session identity | session identity（会话身份） | 会话身份 |

API 标识符、结构体名和协议字段不翻译。概念名称与代码名称同时出现时，用代码格式标出代码名称。

### 相近概念必须主动区分

Wirelink 中有多组名称相近但保证不同的概念。第一次用到其中一项时，应指出最容易混淆的边界：

- latest 说明保留哪个值；reliable 说明链路是否确认投递。
- 链路投递成功不等于 RPC 业务执行成功。
- borrowed view 描述有效期；owned value 描述数据已被复制到调用方可控制的存储。
- endpoint 的推进线程不一定等于业务处理线程。
- adapter 连接传输接口；envelope 定义字节如何封装。

这种区分应贴近第一次使用，而不是只放在页面末尾的术语表。

## 链接与引用

链接帮助读者按需加深理解。它不能代替当前步骤所需的解释。

- 在概念第一次出现的位置放置链接。
- 链接文字写出目标内容，例如“[RPC 业务完成语义](./rpc-runtime-cn.md)”，不要写“点这里”或“更多信息”。
- 教程链接到概念说明；概念说明链接到参考手册；参考手册反向链接到最合适的教程。
- 同一小节不要反复链接同一个术语。
- 外部技术只做完成当前任务所需的简短说明，并链接到其权威资料。
- 延伸阅读放在文末，但完成正文不能依赖读者预先阅读它们。
- 链接到标题或文件时，应说明读者去那里能解决什么问题。

推荐使用三层解释：

1. 当前段落给出一句可继续操作的定义。
2. 概念页面解释心智模型、边界和选择依据。
3. 参考页面列出完整 API、字段和错误条件。

### 页面开头

开头不要先给历史、架构全景或术语清单。先把上一课的结果与这一课的需求连接起来：

> 显示端现在能读到最新温度。接下来，你将让它向传感端发出校准请求，并明确区分“请求已经送达”和“校准已经完成”。

学习目标要写成动作，避免使用无法验证的“理解”“熟悉”“掌握”。可以改用“发送”“比较”“解释”“选择”“排查”。

### 页面中部

每个步骤按“目的—位置—修改—运行—观察”的顺序写。读者在一个步骤内不应猜测：

- 修改哪个文件；
- 命令在哪个目录运行；
- 是否需要替换已有代码；
- 成功输出是什么；
- 输出不同时先检查什么。

长篇原理说明放在读者第一次观察到相关行为之后。若原理超过当前任务所需范围，保留一句边界说明并链接到概念页面。

### 页面结尾

页面结尾完成三件事：

1. 用练习让读者迁移刚学到的能力。
2. 用选择题暴露常见误解。
3. 用能力清单和一个明确的下一步结束。

不要在结尾一次列出十几个平级链接，让读者重新决定学习路径。

## 操作指南与参考手册的写法

教程的循序渐进不应强加给所有页面。已经知道目标的工程师需要快速定位答案。

### 操作指南

操作指南以任务为标题，例如“将 Wirelink 接入非阻塞 UART”。开头列出适用场景、前置条件和最终状态，然后直接给步骤。它可以提供多个方案，但要写出选择依据。

一个操作指南只解决一个可判断完成的任务。背景原理链接到概念说明，完整字段链接到参考手册。

### 概念说明

概念说明先描述需要解释的现象，再给出模型、边界、对比和失败模式。它不要求读者边读边搭建完整项目，但应包含小型、真实的例子。

适合优先补齐的 Wirelink 概念页面包括：

- latest、FIFO 与可靠投递分别解决什么问题；
- 链路投递与 RPC 业务完成的区别；
- borrowed view 与 owned value 的生命周期；
- endpoint owner、执行线程和回调线程之间的关系；
- adapter 与 envelope 的职责边界；
- session identity 如何参与重连与旧数据隔离。

### 参考手册

参考页面保留精度和完整度。每页开头增加：

- 本页定义什么；
- 哪些读者需要它；
- 阅读前应完成哪篇教程或概念说明；
- 哪些章节包含规范性行为。

接口条目应稳定使用“用途、签名、参数、所有权、返回值、错误、线程或 owner 约束、最小示例、相关接口”的顺序。

## 中文语言细则

### 句子和段落

- 默认每段一至三句话。复杂条件改用列表或表格。
- 条件放在动作之前，例如“当队列已满时，检查返回码”。
- 主语可能不清楚时，明确写“应用”“endpoint”“adapter”或“回调”。
- 少用括号承载主要信息。重要条件写成独立句子。
- 缩写首次出现时写出全称或普通语言解释。
- 中英文之间的空格遵循仓库统一格式；代码标识符使用反引号。

### 肯定陈述优先，否定只用于边界

描述一个概念时，先说它是什么。不要用“它不是 X”来定义 X：读者关心的是概念的正面含义，不关心它不是什么。

按四类处理解释性正文里的否定：

- **反义定义**：改写成肯定句。“它不是 31 个字符，也不会动态分配内存”改为“上限按字节计，一个多字节字符会占用多个字节；存储是结构体内的固定容量数组”。
- **伪范围否定**：删除。“`saved` 不会反向指向 `response` 或 endpoint”在前一句已经说明赋值会复制全部字节，直接删除，或改为“`saved` 是一份独立副本”。
- **场景性警告**：保留，但移出正文。把“如果文本来自外部输入，复制前必须检查字节长度”放进 **注意** 提示框或课后选择题，正文只留肯定描述。
- **真正的边界**：保留，并先肯定、后对比。相近概念的区分（例如“链路投递不等于 RPC 业务完成”“session identity 不是认证”）本身就是信息，不能删除；应先写清它是什么，再用一句对比点出最容易误解的边界。

选择题的错误选项反馈、失败模式列表和边界表本来就在解释否定，不适用本节。判断标准：这句否定是在描述概念本身（改写或删除），还是在提供读者必须知道的边界（保留并调整顺序）。

### 规范强度

必须准确区分约束和建议：

- 协议或 API 的硬约束使用“必须”“不得”。
- 推荐默认值使用“建议”“默认选择”。
- 多种合法方案使用“可以”，随后给出选择条件。
- 行为描述直接用陈述句，不用“应该会”。

如果文档写“必须”，应能链接到 API、协议或实现约束。作者偏好不能伪装成规范要求。

### 提示框

提示框只用于真正偏离主线的信息：

- **说明**：补充理解所需但不属于步骤的信息。
- **技巧**：可选的效率改进。
- **注意**：可能导致数据损坏、安全问题或难以恢复错误的情况。

完成当前步骤必需的信息必须写在正文中。不要把大段核心说明折叠或全部放入提示框。

## 评审清单

提交新的公开文档或重构现有文档前，作者和评审者应逐项检查。

### 页面定位

- [ ] 页面明确属于教程、操作指南、概念说明、参考手册或维护者资料。
- [ ] 标题说明任务或主题，没有依赖“第一篇”“进阶篇”才能理解。
- [ ] 开头说明目标读者、前置知识和完成结果。
- [ ] 页面只承担一个主要任务或概念轴。

### 递进与概念

- [ ] 当前任务依赖的前置知识已经教授并链接。
- [ ] 每个新术语在首次出现处被解释或链接。
- [ ] 抽象概念在具体需求或可观察行为之后出现。
- [ ] 相近概念的保证和边界被主动区分。
- [ ] 非必要的底层细节没有打断主线。

### 步骤与代码

- [ ] 每个步骤说明目的、文件位置、操作和预期结果。
- [ ] 每个代码块之前都有独立的引导句。
- [ ] 示例使用真实名称，并只包含当前任务所需配置。
- [ ] 示例可以构建或由自动化检查验证。
- [ ] 错误路径给出可识别现象和恢复办法。

### 语言与导航

- [ ] 句子直接、具体，避免无意义的修饰和模糊情态词。
- [ ] 定义使用肯定句，不用“不是……”“不会……”来定义概念。
- [ ] 正文不回答读者没有提出的问题。
- [ ] 场景性警告放在提示框或练习中，不打断主线。
- [ ] 链接文字能说明目标页面内容。
- [ ] 读者不需要打开所有链接才能完成当前页面。
- [ ] 页面结尾包含能力检查和一个明确的下一步。
- [ ] 中文与英文页面使用同一信息架构和术语表。

### 教程专用

- [ ] 读者能在早期运行一个工作基线。
- [ ] 每次修改后都有可观察结果。
- [ ] 本课包含一个可独立完成的小练习。
- [ ] 知识题检查应用或预测能力，而非 API 名字记忆。
- [ ] 后期课程只减少读者已经练习过的支架。

## 建议的重构顺序

重构应先解决导航和概念依赖，再润色句子。否则页面会变得更易读，却仍然让读者走错路径。

### 第一阶段：建立路径

1. 给现有页面分类：教程、操作指南、概念、参考、维护者资料。
2. 修复教程编号冲突，改用稳定的任务标题。
3. 建立中英文统一术语表。
4. 将 README 收敛为产品判断、快速运行和路径选择。
5. 从公共学习路径移出 benchmark 历史、审计记录和内部进度。

### 第二阶段：重构核心教程

1. 保留并收紧“最新温度”的可运行主线。
2. 让 RPC 教程复用相同项目，并显式连接上一课。
3. 将 RPC 值生命周期独立为所有权课程。
4. 将 async/deferred 放到同步 RPC 之后。
5. 拆分当前集成教程中的 adapter、owner、session 和 diagnostics。
6. 为每课增加练习、知识检查和能力清单。
7. 应用“肯定陈述优先”：把反义定义改写为肯定句，删除伪范围否定，把场景性警告移入提示框或练习。

### 第三阶段：补齐概念与参考之间的桥梁

1. 按本指南列出的六组相近概念建立概念说明。
2. 在参考页面增加前置教程、所有权、错误和执行约束。
3. 从概念第一次出现的位置添加描述性链接。
4. 运行链接检查，并验证中英文导航一致。

### 第四阶段：增加交互层

在内容结构稳定后，再引入文档站和交互组件。可使用 Astro Starlight 承载导航、搜索和多语言内容，并实现以下轻量组件：

- 单选或多选知识题，提交后解释每个选项；
- 每课能力清单；
- 本地保存的教程进度；
- 可折叠的提示与参考答案；
- 可复制命令与明确的文件名标签。

交互组件必须在纯 Markdown 或 GitHub 页面中仍保留核心信息。JavaScript 失效时，读者至少应能看到题目、选项和答案说明。

## 不必照搬 Astro 的部分

Wirelink 面向嵌入式和系统软件开发者，语气可以比 Astro 教程更克制。无需复制角色故事、表情符号或频繁感叹，但应保留具体场景、即时反馈和循序递进。

参考手册也不必改写成教程。它需要完整和精确；改进重点是明确入口、前置知识、稳定术语和跨页链接。
