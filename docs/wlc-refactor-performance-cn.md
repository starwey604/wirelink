# WLC B/C 重构后的性能复核

日期：2026-09-09。用户在 [B/C 正确性验收](wlc-refactor-progress-cn.md)完成后授权本轮计时。
比较对象是 A 最终保留版本与 B/C 重构版本，**不是游标优化之前的版本**。
不修改算法、产品 pin 或公开 API，不提交/推送、合并 main、创建 tag。

## 产物边界

先在新目录生成、构建并通过 smoke，再开始计时，旧材料不覆盖。
以下产物通过 `cmp`，不是仅比较文件大小：

- codec 全矩阵主机可执行文件。
- 1/12/64 服务、1/4 槽、reliable/unreliable 的五种 API 可执行文件，以及 UDP 程序。
- H7 LTO `zephyr.bin`：重构前后完全相同。ELF 带有不同构建目录的调试信息，
  不将 ELF 文件摘要差异当作机器码变化。

因此本轮这些运行时测试的前后差异不能解释为 B/C 引入了不同指令或布局。
WLC 本身的可执行文件不同，需要单独测生成开销。

## 测量分阶段

Linux x86-64 / Intel Core 5 315，GCC 16.2.1 / -O3 / 无 LTO，
Google Benchmark 1.9.5（`192ef10025eb2c4cdd392bc502f0c852196baa48`）。
WLC 为 Rust 1.96.1 的 Release 构建。

1. 全部构建及正确性 smoke 完成：codec 2/2、主机/API 13/13。
2. H7 实机采集；结束后 reset/halt、关闭 RTT 与 J-Link。
3. WLC CLI：CPU 1，1/12/64 服务 × codec/runtime-only/combined，
   每种输入预热后做 7 轮 A/B/B/A，共 252 次计时，每侧每种输入 14 次。
4. codec：CPU 1，108 组 × 7 重复，最短 0.05 s，A/B/B/A。
5. API：CPU 1，五种配置共 44 组 × 7 重复，最短 0.05 s，A/B/B/A。
6. UDP：CPU 0/1，四种 payload，每种 3 轮，每轮 200 次预热 + 2,000 次调用，
   A/B/B/A。只将其解释为本机两进程端到端结果。

codec/API 使用随机交错重复；只有一个 benchmark 进程运行，不并行构建、CTest、
Twister、其他 benchmark 或 H7 采集。不修改系统 governor、全局 ASLR 或用户其他进程；
保存采样前后 affinity、负载、CPU 频率和 `/proc/stat`，并报告同一版本重复漂移。

## WLC 生成开销

统计的是新进程的 user + system CPU，包括启动、解析、校验、生成和文件写入，
不是只包围 emitter 的计时。文件系统已预热，不做 fsync，不代表冷磁盘性能。
各输入的两版本生成产物也逐文件校验一致。

| 服务数 | runtime-only CPU 中位数 | combined CPU 中位数 |
| --- | --- | --- |
| 1 | 1.282 → 1.019 ms（−20.5%） | 1.682 → 1.357 ms（−19.3%） |
| 12 | 4.095 → 2.698 ms（−34.1%） | 5.125 → 3.553 ms（−30.7%） |
| 64 | 16.084 → 9.719 ms（−39.6%） | 20.198 → 13.758 ms（−31.9%） |

runtime-only 不再生成后丢弃 codec，模板也不再多轮扫描/复制完整字符串。
七轮各自的配对 CPU 变化范围：1 服务 −25.8%～−15.7%，12 服务 −36.5%～−28.0%，
64 服务 −40.8%～−38.9%；并非依赖单次最低值。64 服务 runtime-only 的 wall 中位数
为 18.922 → 12.436 ms（−34.3%），但不把它等同于端点 RPC 延迟。
纯 codec 的差距明显较小，不作为本轮主要收益。原始 `ru_maxrss` 有相同的启动高水位，
不据此声称 WLC 的堆峰值或分配次数改善。

## H7：代码不变的实机确认

STM32H723ZG / dm_mc02、550 MHz，Zephyr SDK 1.0.1 / GCC 14.3.0、
-O2、LTO、I/D cache 开启。真实构建参数含 `-flto`。
FLASH **62,012 B**、RAM **104,960 B**，均不变。

两次独立启动各 225 组 × 5 样本，完整矩阵/计数/成功标记通过既有严格校验器。
这两次运行使用相同机器码，不伪装成两个不同候选固件。

| 操作 | 启动一 / 启动二（µs/操作，中位数） |
| --- | --- |
| 热入口，两字段正序解码 | 1.006 / 1.006 |
| 热入口，连续 16 字段正序解码 | 6.142 / 6.140 |
| 热入口，稀疏 16 字段正序解码 | 7.118 / 7.108 |
| 热入口，packed float32[30] 解码 | 1.196 / 1.196 |
| 冷入口，两字段正序解码 | 2.138 / 2.133 |
| 混合正序解码 | 9.278 / 9.281 |
| 混合逆序解码 | 10.684 / 10.678 |

225 组的重复变化中位数为 −0.011%；最大绝对百分比约 2.24%，发生在
约 79 ns 的常量测长，绝对差 1.76 ns，约一个 H7 周期。不是新的 2.24% 算法回退。
冷入口是受控 I-cache 失效条件，不能替代硬件 miss 计数或 Willow 整机 CPU。

首次读取的板载内容与本轮镜像不符，已烧录并 verify 成功。
`h7-confirm-b.log` 混入复位前 RTT 残留/非 UTF-8 数据，被拒绝，不删除乱码后冒充有效采样；
重新启动前清除测试用 RTT 控制块签名，取得完整有效的 `h7-confirm-c.log`。
正式统计只用 `h7-confirm-a.log` 和 `h7-confirm-c.log`。
板上最后保留此 codec benchmark，**不是 Willow**；已 reset/halt 并退出调试连接。

## 主机与 UDP

所有捕获通过矩阵完整性、重复编号、错误标记、上下文、编码长度和资源/时钟计数检查。
CPU 指标均为每组七次重复的中位数，下面的“全矩阵中位数”再对组间变化取中位数，
不是总体吞吐增益。

### 主机微基准：不能作为严格百分比性能门禁

| 矩阵 | A / B 配对的全矩阵 CPU 变化中位数 | 同一版本两次启动的最大绝对漂移 |
| --- | --- | --- |
| codec，108 组 | +1.33% / −0.01% | A 版 91.58%，B/C 版 9.59% |
| API，44 组 | +0.08% / −0.56% | A 版 6.88%，B/C 版 8.71% |

codec 的异常不是只发生在一个离群样本：同一旧版二进制的 packed30、pattern 2 解码
两次启动 CPU 中位数为 **17.951 → 34.389 ns**，每次内部七个样本分别落在
17.751–18.321 ns 与 33.773–34.701 ns。packed30 正常输入也从 14.829 → 27.526 ns，
但两字段解码仅从 9.614 → 9.788 ns，连续 16 字段从 58.336 → 59.399 ns。
不能解释为所有操作统一降频，也不能据此唯一断定 ASLR、cache 或某个后台进程是根因。

计时期间没有其他 agent 构建/测试/采集，但主机仍有桌面后台活动，使用
`intel_pstate/powersave`、普通 ASLR；不是隔离的固定频率 runner。
各组内部重复看起来稳定，仍不足以保证跨进程重复性。
本轮不反复重跑直到数字满意，不用 −46.6% 的配对“收益”宣称 packed30 得到优化。
**前后机器码完全相同证明 B/C 未改变这些运行路径；本机计时则仍不足以给出 3%/5% 精细门禁。**

12 服务/4 槽/reliable 的完整 API 参考值：

| 操作 | A 配对：重构前 → 后（µs） | B 配对变化 |
| --- | --- | --- |
| 0 B 单 RPC | 1.157 → 1.156 | −3.79% |
| 32 B 单 RPC | 1.410 → 1.399 | −1.95% |
| 512 B 单 RPC | 5.252 → 5.242 | −1.12% |
| 1024 B 单 RPC | 9.276 → 9.246 | −0.47% |
| 32 B 四调用批次 | 5.113 → 5.147 | −2.36% |
| 512 B telemetry | 2.046 → 2.041 | −0.81% |

四调用一行是每批时间，不是每调用时间。初始化/空闲等短路径存在更大百分比变化，
没有从全矩阵中剔除。端点大小 **24,624 B**、arena **10,902 B**；
单 RPC/四调用批次/telemetry/idle/初始化的协议时钟读取数分别为 **9/24/2/1/0**，
四份捕获严格一致。五种配置的其他资源与时钟计数同样通过一致性检查。

### 两进程 UDP：记录当前延迟，不声称加速

每份捕获覆盖 4 种 payload × 3 轮 × 2,000 次成功调用，共四份，合计 **96,000 次**
计量窗口内调用；预热和测量边界 RPC 另计。下表是 B/C 两次捕获分别对三轮统计取中位数。

| payload | p50（µs） | p99（µs） |
| --- | --- | --- |
| 0 B | 7.765 / 7.578 | 16.728 / 15.609 |
| 32 B | 8.002 / 7.891 | 21.147 / 18.297 |
| 512 B | 15.230 / 15.224 | 29.489 / 26.493 |
| 1024 B | 19.821 / 19.765 | 32.648 / 34.491 |

前后两组配对中，各 payload 的 p50 变化范围为 −1.61%～+2.30%，p99 则约
−12.66%～+9.24%，尾延迟仍有噪声。客户端与服务端 CPU 时间也已记录，例如
B/C 的 1024 B 每调用分别约 10.58–10.60 µs、11.37–11.39 µs。
它们在不同进程并行执行，不能相加当作 RTT；这些数值也不代表真实串口或 H7 CPU。

## 结论与剩余项

- B/C 的可维护性拆分没有改变本轮覆盖的主机/固件机器码、内存配方或 ABI。
- WLC 的 runtime-only / combined 生成确有稳定 CPU 收益，尤其在服务数量较多时。
- H7 重复采样符合原有性能水平；A 之前留下的大消息逆序与 packed30 布局取舍未被本轮“修复”。
- 主机微基准的跨进程重复性仍需单独诊断，不能通过调整生产 codec 迎合这一轮数字。
  下一步若要设置严格性能阈值，应先建立稳定 runner，并区分进程布局、调频与调度因素。

计时后的 codec 2/2、主机/API 13/13 smoke 再次通过；冻结编译器对照的 41 个 C/H
快照再次通过，编译器及运行时二进制摘要未变。没有将 smoke 打印的计时混入正式统计。
