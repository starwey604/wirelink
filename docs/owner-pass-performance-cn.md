# Owner pass、通知与有界批处理

日期：2026-09-09。范围限于 host executor、诊断和主机基准；不修改 C 核心、WLC、
线上格式、生成 ABI 30 或产品依赖。本轮没有推送、合并 main、创建 tag 或操作 H7。

## 先测，再改

新增默认关闭的 `WIRELINK_HOST_ACTIVITY`，记录 pass、事件、RPC 收集/完成、LATEST
尝试/接受/背压、通知和等待原因；不读取时钟、不在热路径打印。计数不是 OS 上下文切换。
OFF 不保留诊断原子数组，不执行计数加法；host C++ 布局/头文件变化要求统一重编。

先冻结原调度实现加相同计量字段的二进制，再实验；没有把修改后的程序当作基线。
独立 [harness](../benchmarks/owner_pass/README.md) 用首轮 gate 预置已经到达的数据，
业务提交后没有等待凑批。主机多生产者基准另外记录 submit→sink 的存活更新年龄。

`no_reported_work` 只表示没有 pump 报告的进展、LATEST 推进或收集到的 RPC；
最后一次确认空闲、未单独报告的 adapter 工作也可能落入其中，不能直接称为无效 CPU。
通知总数包含 start/stop；一次通知不等于一次线程切换。事件数、端点 step 数、
executor pass 数也不是同一种计量。

## 落地的减法

1. **LATEST 每轮最多 2 条**，只取当前可用数据。每条仍使用现有 acquire-copy/complete
   所有权协议，发送及回调不持有 outbox mutex；每条检查停止，遇背压立即结束本批。
   预算耗尽就回到 RPC 收集、adapter service、RX/协议 deadline 和应用推进。
2. **不因历史事件无条件再跑一次**。raw hooks 的应用回调显式要求续跑时继续；否则查询
   现有就绪/deadline 提示，再执行防丢唤醒的 generation 检查。没有 service，或 service
   提供了就绪提示的接入，可省掉仅由已消费事件触发的尾部 pass。
3. **保留必要的推进机会**。LATEST 在 service 之后启动异步发送时，再给 service 一轮；
   若仍背压便等待通知。没有就绪提示的旧 service hooks，以及可能聚合多个端点的 custom
   driver，仍保留原 progress 规则，不能从最后一个端点的状态推断整个 driver 空闲。
   RX 回调启动异步回复的两种接入均有回归测试。
4. **成功的零长度 feed 不通知**。部分接受和零接受的溢出/背压仍通知，以便 owner
   处理 RX 恢复状态。没有删除外部 adapter 的显式 `notify()` 合同。
5. **RPC pending 在收集锁内清理**。原来在获取锁之前 exchange(false)，可能把本轮
   已经取走的并发入队留下的 true 带到下一轮，造成空收集。现在在同一 admission mutex
   内标记完现有 jobs 后 store(false)；后续生产者只能在解锁后重新发布 true。
   保留空队列 acquire-load 快速路径，去掉每次收集的 exchange RMW。

不增加业务开关，不改为无锁队列。RPC 仍最多收集 8 个已就绪 job；同步调用仍有入队和
结果返回两个逻辑边界。结果 CV 通知仍在 mutex 内，保护调用方栈上 job/CV 的存活期。

## 可重复的工作量结果

以下是冻结基线与候选的受控记录，不是耗时百分比：

| 已就绪负载 | 原 pass | 新 pass | 说明 |
| --- | ---: | ---: | --- |
| 单条 LATEST，同步 sink | 3 | 2 | 不等第二条到来 |
| 8 条不同 ID 的 LATEST，同步 sink | 10 | 5 | 四轮各发 2 条，再消费完成事件 |
| 8 条 LATEST + 8 条 RX | 10 | 5 | RX 正确消费，不被批处理吞掉 |
| 8 条 LATEST，单缓冲异步 sink，有提示 | 10 | 9 | 物理缓冲仍只能逐条发送 |
| 上项加初始背压，有提示 | 11 | 10 | 等待两次，恢复通知后排空 |
| 64 次成功零长度 feed | 2 | 1 | 通知 66→2，剩余是 start/stop |

纯 RX burst 的 2 次 pass 保留：测试在 pass 开始后发布 RX，generation 变化仍需检查，
不能为了漂亮的计数丢掉竞态保护。线程启动通知自身也可能影响纯 idle 的次数。
连续补充测试发送 9 条、在第 1 条后注入 RX，并在第 2 条后处理待收集 RPC；
最终 5 个 pass 完成，批内最多 2 次 sink 调用，停止无需排空所有潜在生产者。

**异步代价没有消失**：2 条预算会在第一条占用异步缓冲后探测下一条，得到 BUSY。
8 条异步负载的尝试数从 8→15；初始背压从 9→16。这些额外尝试不等于更多物理发送，
也不会造成持续空转。无就绪提示的旧式异步接入仍需 10 个 pass。当前未为这点增加
公开 TX-ready API 或维护第二套传输状态；实际 USB/板端 CPU 收益不能由此直接推断。

## RPC 与跨线程交接

插桩诊断采用 32 B、每生产者 300 次、1/8 生产者，饱和及每生产者 1 kHz：

- 收集标记修正前，8 生产者 RPC 有 6/17 次空收集，proxy 有 5/26 次空收集
  （分别是饱和/定频，均为 2400 次调用）。这是可定位的多余取锁，不是网络重试。
- 单生产者真实 RPC 约 2 个 executor pass/调用；即时 proxy 约 1 个。
  当前基准 driver 每 pass 又主动 step 两对端点，共 4 次。不能把 wrapper 的这些调用
  都归因于 executor；本轮未改变此驱动策略来制造 RPC 加速。
- 多生产者已经自然形成非空批次。pending 修正后的 `rpc_empty_collections == 0`
  作为并发正确性断言，结果完成数必须等于提交数；不通过增加等待扩大平均批量。
  最终修正验证的 8 生产者饱和/定频 RPC 和 proxy，空收集均为 0。

后续若继续收敛 driver pass，应先明确“已处理过事件”和“仍需继续推进”的独立合同，
覆盖多端点 driver、回调串联、异步传输和 deferred RPC。不能直接删除 `progress` 续跑。

## CPU / 交付年龄与限制

使用 [串行配对脚本](../benchmarks/api/executor_pair.py)：四种模式、1/8 生产者、
32/512 B、饱和/每生产者 1 kHz、三次重复，每版 96 个进程；饱和每生产者 3000 次、
定频 300 次。基线和候选均关闭 activity、lock 和 broad timing 插桩，保持相同的
payload 时间戳及 sink 校验。编译、CTest、Zephyr 与采样不并行。

共享桌面存在明显调度波动；CPU 和 p99 不能据此建立稳定百分比结论。饱和 LATEST
的实际交付数还受 coalescing 影响，不能把 CPU/submit 降低自动理解为处理效率提升。
计数减少是本轮确定结果，**不是所有传输/负载更快的保证**。

sink 年龄包括排队、编码和基准 sink 解码；不含真实链路/远端处理，被替换掉的更新
没有样本。它不是持续 AoI，也不能替代 H7 或产品链路性能验证。

### 为什么最后选 2 条，而不是最初的 4 条

最初 4 条预算能把受控 8 条 burst 压到 3 个 pass，但一次完整配对矩阵的
8 生产者/512 B/1 kHz 组，sink p99 中位数出现 61.29→290.29 µs 的回退。
没有把这个信号简单删除或归咎于噪声，随后冻结 1/2/4 条三个候选，与基线随机交替
复测该组：每生产者 1000 次、各 9 次重复，共 36 个进程。

| 版本 | CPU/submit µs，中位数 [min,max] | sink p99 µs，中位数 [min,max] |
| --- | --- | --- |
| 基线 | 10.54 [6.90,11.04] | 90.07 [40.00,164.48] |
| 1 条，含其余调度修正 | 10.31 [7.02,10.75] | 62.33 [50.07,144.34] |
| 2 条 | 10.24 [6.93,10.78] | 60.25 [39.07,136.13] |
| 4 条 | 10.46 [7.24,10.53] | 62.91 [41.13,188.67] |

接近 300 µs 的现象未稳定复现，不能据此认定根因就是预算 4，也不能宣称尾延迟问题
已被证明彻底消失。各版 CPU 区间重叠，4 没有可确认的 CPU 优势；因此最终选择 2，
保留更多 RPC/RX 调度机会，同时将受控 burst 的 pass 数减半。这里的 2 是有证据支持的
保守默认，不是跨平台最优值证明；未增加业务可调的批处理开关或人为等待。

最终预算 2 又完成一轮完整矩阵，192 个进程全部校验通过。以下列出四个定频 LATEST
组的三次中位数，保留改善和变慢两种结果（每生产者 1 kHz，单位 µs）：

| 生产者 / payload | CPU/submit，前→后 | sink p99，前→后 |
| --- | --- | --- |
| 1 / 32 B | 18.85→19.00 | 32.80→33.23 |
| 1 / 512 B | 17.56→21.14 | 34.87→27.21 |
| 8 / 32 B | 10.64→9.99 | 80.02→60.19 |
| 8 / 512 B | 10.00→11.08 | 60.94→66.93 |

这也说明本轮不能作为普遍 CPU 提速结论。后续仍应在受控目标平台上验证 CPU 和尾延迟，
而不是把逻辑 pass 减半写成 CPU 减半。

## 验证与本机证据

- Release 教程/host/UDP/C/C++/FFI：20 项；独立计数与四种 executor 负载另行测试。
- 有界调度 harness 覆盖 14 个 JSON 场景和 1 个 overflow 恢复断言场景；
  连同四种 executor 负载、报告分析测试，共 6 项各重复 100 次。

  runtime 导致加载失败；复测显式 preload 匹配的 clang runtime，仅 Python 关闭 leak
  检查，不能把最初的加载失败说成库内存错误。
- TSan：核心/host/通知/有界调度 5 项；另检查真实 RPC/proxy/LATEST/shared 多生产者。
- 安装消费：OFF 和 ACTIVITY+LOCKS 各 3 项，校验导出宏和新头文件，实际 start/stop。
