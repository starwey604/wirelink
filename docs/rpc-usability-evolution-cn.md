# RPC 易用性与内存所有权演进计划

日期：2026-09-06，实施更新：2026-09-07。状态：**M0/M1 完成，M2 实施中**。
基线为 Wirelink `d245cbe`、WLC `b5c444a`、生成 ABI 21。
此前的[三批时钟改造](endpoint-clock-evolution.md)已完成；本文是下一轮工作。
实施证据与已完成/待完成项见[实施记录](rpc-usability-progress-cn.md)。
本次授权执行到 M2 软件验收和 H1 准备完成；**在需要 H7 功能验证时停止，不烧录**。

## 目标与范围

客户端只描述“调用什么、等多久、如何接收结果”；服务端只描述“收到什么、返回什么”。
默认 RPC 不要求用户管理调用槽位、借用字段或手动释放结果。

- 默认业务对象拥有有界数据；借用视图和延迟回复是明确选择的高级能力。
- 默认端点预分配存储，业务路径不调用分配器。可选创建层支持自定义分配器。
- 核心保持无堆、无 OS 依赖；同步等待留在平台集成层，仍由单一执行者推进通信。
- 不为兼容保留两套普通门面，但保留确有用途的高级机制。
- 只在 dev 演进，不合并 main、不打 tag、不发布；M0–M2 不修改产品仓库。

## 已核实的问题

1. 当前 RPC 会把收到的响应复制进内部管理的槽位，但解码后的 string/bytes
   仍指向槽位。直接在 inspect 后自动释放不成立，需改变结果表示或复制边界。
2. 当前本地产品 schema 的 31 个 RPC 中，2 个设备信息响应含有界短字符串；
   较大的 `bytes<2031>` 位于升级 bulk 路径。这个样本不代表所有用户，但不支持
   为普通控制 RPC 一律强制借用模型。
3. 默认一缓存槽、REJECT_NEW，叠加教程的 10 秒 TTL，在同一会话连续调用时
   可得到 CACHE_FULL。此前使用现有 FFI 组件已复现：首次得到 42，第二次
   服务端返回 -1008，业务 handler 未执行。不能只把配置数字移入 defaults。
4. 客户端五种终态的组合判断、release，以及服务端 token/complete/delivery，
   都在入门代码中暴露；默认端点配置仍包含完整 runtime 装配细节。
5. 核心只有一个应用 TX 槽。增加 RPC 槽位不等于增加链路发送窗口；自动回收
   必须和有界提交队列、独立 TX 完成、适配器借用结束配套设计。

代码入口：`wlc/src/codegen.rs`、`runtime_codegen.rs`、`endpoint_codegen.rs`、
`managed_rpc*.in`，以及 `src/rpc.c`、`src/endpoint.c`、`runtime/host/`。

## 先确定的设计方向

### 数据和结果所有权

- 普通请求与响应使用 WLC 生成的自持值：有界 string/bytes 内嵌数组和长度，
  嵌套消息递归拥有数据，普通结构体赋值后不能残留指向原对象的内部指针。
- 字符串长度按字节计，保留 UTF-8、空值、presence、嵌入 NUL 等现有语义；
  即使增加末尾 NUL 便利，也不能用 strlen 改写协议长度。
- 同步结果独立于 RPC 槽位和 endpoint 生命周期；异步回调参数仅在回调期间
  有效，但复制其自持值即可长期保存。不能宣称 C 指针没有任何有效期限制。
- 异步提交在返回“已接受”前完成请求快照，不长期借用调用者栈变量。
  服务端响应先转入框架拥有的存储，再离开处理流程。
- 复用 codec target 中的值定义与编解码支持，多个 runtime 不重复生成同一业务类型。
  M0 定稿：普通对象为 `<message>_value_t`，高级 codec 视图保留 `<message>_t`。
  值支持 `*_value_clear/encode/decode`；显式高级转换为 `*_value_from_view/to_view`。
  转换失败不修改输出；转换输入输出不得重叠。普通 RPC 不需要这些转换。
- 第一轮覆盖现有可静态推导上限的类型；无界 repeated 或无界字符串不凭空给
  一个容量，不顺便扩展 IDL。大结果和流式数据继续有高级路径。

### 完成、取消与关闭

- 提交返回值表示是否接受；完成结果表示成功、业务拒绝、超时、取消或通信错误。
  不暴露中间发送状态，不用全局或 endpoint.last_error 承载某次调用的错误。
- 已接受调用在持续驱动或有序关闭中恰好通知一次；提交失败不触发完成回调。
  默认无需 release；需要取消时才获取可选句柄。
- 先形成独立完成快照、回收 RPC 调用资源，再交付回调；仍由原 owner 排空
  独立链路终态，不能提前复用 DMA/适配器仍借用的 TX 内存。
- 回调可提交或取消其他调用；新调用受明确容量限制，队列满立即返回 BUSY。
  不能递归 step 或阻塞等待同一个 owner。关闭在 owner 安全点完成，回调中
  可以请求停止，但不能同步销毁正在执行自身回调的对象。
- close 停止接收新调用，结束在途通知并 quiesce；返回后无回调、无借用访问。
  超时/取消不撤销远端副作用，新调用也不等于业务幂等重试。

### 默认配置与缓存

- 普通配置只要求 session、clock、业务 handler/context；内部可靠发送参数和
  RPC 角色装配由默认端点负责。client 能力在初始化时准备，注册 handler 即
  提供相应 server 路由；不在首次调用时隐式重新分配或重组端点。
- M0 定稿：默认采用“有限最近结果缓存”，允许淘汰最旧且已送达的响应；不淘汰
  未完成、待发或仍在传输中的响应。TTL 是最长保留限制，不承诺完整 TTL
  窗口内永不淘汰。这是相对 ABI 21 默认 REJECT_NEW 的显式行为变化。
- 严格保留窗口的产品仍可选 REJECT_NEW，并明确配置容量、负载和背压。
  M0 对 1/4/8 缓存槽完成尺寸及压力测试；选择四槽默认，保留可缩小的静态容量，
  具体 RAM 代价见实施记录。不宣称通用工业参数。
- 本地入队失败、远端忙、业务拒绝不得混淆。至少提供服务端资源耗尽诊断和
  确定的客户端截止时间；若增加远端 BUSY 报文，必须单独审阅 RPC 线上语义，
  不能借业务拒绝码悄悄编码一种新的框架错误。
  M0 决定本轮不新增远端 BUSY 报文；服务端资源不足保留本地诊断，客户端按原截止时间完成。

### M0：先把可检验的行为定下来

准备三个贯穿后续阶段的场景：Add 数值 RPC、DeviceInfo 式有界字符串 RPC、
接近单帧上限的 bytes 响应。再加一项延迟服务，覆盖取消、超时和迟到完成。

记录 ABI 21 的静态大小、栈使用、复制次数、时钟读取次数与现有 H7 测量条件。
自持类型的最大内存大小与最大编码大小分别计算，不能混用。共享解码/通知暂存
尽量按最大服务计算，不给每个 RPC 都复制一整套最大缓冲区。

M0 必须定稿两项实质选择：缓存满时的默认语义，以及是否在本轮增加远端 BUSY
表达。没有单独通过线上语义审阅时，M1–M4 保持现有正常请求/响应格式。

### M1：先消除借用结果的限制

覆盖空值、最大长度、超界、嵌套消息、packed 数组、缺失 required、非法 UTF-8。
复制结果后，改写原输入、复用槽位、close/reinit endpoint，保存的结果仍应正确。
无效输入不能留下部分有效的成功结果。历史向量作为交叉编解码基准，不因新 C
布局修改旧字节。普通结果不得要求用户拼装 backing buffer 或调用销毁函数。

### M2：合并完成路径，不增加第二套 RPC 状态机

普通 handler 填写预初始化的自持响应并返回“成功/业务拒绝”；token 只出现在
延迟处理入口。框架仍在执行业务前预留回复能力，背压不能导致重复执行 handler。

异步客户端复用底层超时、去重和取消逻辑，增加有界完成交付及请求排队；请求
截止时间从 API 接受时起算，包含排队时间，发送时不能重新开始 RPC 超时。
现有 inspect/token/release 转入高级入口，不保留大量等价普通别名。

测试必须覆盖请求已执行但 ACK/响应丢失、响应先于请求 TX 终态、通知中再提交、
队列满、乱序回复、取消与完成同一轮到达、close 时全部调用的唯一通知、旧句柄
和旧 token、端点重建、缓存淘汰后的保护边界。入门示例不得再手写五种终态判断。

### M3：等待能力属于平台，不属于 C 核心

先完成 UDP 单 owner 同步调用，使用适配器就绪等待和端点 deadline；再接入
host executor 的线程安全提交代理。业务线程不直接碰 endpoint，不能用一把锁
围住长期阻塞调用，让真正的 owner 无法处理响应。

为 Zephyr 提供最小线程/事件等待集成，供 H2 验证；其他 RTOS 暂不同时承诺。
平台选型和等待原语只在初始化时设置。统一接受时刻、排队时间、RPC 截止时间、
重传和唤醒；无工作的等待不能靠固定 1 ms 轮询。禁止从同一 owner 回调调用 sync，
且失败不能破坏已有调用。手动时钟测试必须能推进并唤醒，不绑定墙上时间。

### M4：分配器是存储来源，不是新的消息生命周期

保留静态生成端点，同时提供可选创建层，由 C 兼容的 allocator 描述符在初始化
申请所需对象/池，destroy 统一释放。两条路径共用同一运行逻辑。

描述符说明 context、size、alignment 和配对释放规则；不使用全局 allocator，
不在运行期间替换。对象及其内部引用在创建后地址稳定；allocator context 需活到
destroy 完成。协议缓冲区与 adapter 特殊 DMA 内存各归其层，不把普通 allocator
默认为任何硬件 DMA 都可访问。

不做逐字段 malloc、逐包 realloc 或隐式回退到系统堆。逐个分配点注入失败，检查
回滚、无泄漏/双重释放、没有回调逃到 destroy 之后。C++/Python 绑定负责自己的
对象生命周期；不在这一步扩成完整 SDK、共享引用对象系统或无限结果历史。

### M5：产品迁移和文档最后收敛

先检查 libflorid main 是否有需同步的变更，再按此前约定同步到其 dev；仅更新
libflorid、Ragtime_Firmwares 的 dev 依赖和调用点，保留原长期测试的版本与记录。
迁移需识别当前产品的显式字段映射模式，不把切换托管 RPC 当成无线上影响的改名。

教程继续保留 `00_telemetry`、`01_rpc` client/server 两程序；RPC 先展示主机同步
调用，再单独讲异步客户端和延迟服务。增加字符串响应示例，证明简化并非只适用于
加法。同步更新中英文、完整可编译代码、安装步骤与测试，用户不需要嵌套 wlc worktree。

## 实板检查安排

- **H1，M2 后**：独立 H7 sample；连续数值/字符串 RPC、结果复制后复用槽位、
  自动回收、拒绝、超时和缓存压力。板内 loopback 只证明目标 CPU 上的实现。
- **H2，M4 后**：同一 H7 上验证 Zephyr 任务等待、停止唤醒、固定池初始化、
  分配失败，以及 idle/encode/decode/完成通知/复制的周期和栈高水位。
- **H3，M5 后**：主机到 H7 实际可用的 USB 或 UART 链路，验证产品类型化 RPC、
  断连重连、背压和退出。按 [adapter HIL](adapter-hil.md)记录双方计数；未实测
  的传输不标为已通过。

每次实板之前先通过相应软件门槛。Windows 使用当前已授权的
`moonf@192.168.8.5` 和 J-Link；直接烧录，不把备份设为前置条件。
先自动连接，必要时尝试已验证可执行但不能保证恢复连接的设备重启脚本；失败后
明确请求用户拔插/按 RESET，不反复盲重试，也不把连接故障当成库测试失败。

性能记录包括：配对提交、板型/频率、编译选项、缓存/中断状态、消息大小、循环数、
RAM/栈、复制与分配次数、时钟读取次数、CPU/周期及端到端延迟分位数。
区分 IRQ 开启的整体开销、可隔离的 CPU 路径和物理链路延迟；不拿 host 或 QEMU
数值替代固件结果，不将旧 1.93 μs idle 观测当成严格的纯 CPU 基准。

## 版本与完成条件

- 首次改变公共生成接口/布局时从 ABI 21 升级；预期下一版为 22。后续检查点
  如再次改变布局，继续递增，不能复用同一 ABI 标识不兼容的生成产物。
- 每个可消费检查点固定 Wirelink/WLC 配对 SHA，并更新 CMake、manifest、
  fixtures、安装文档和两端 CI。ABI 更新不是线上格式或产品迁移兼容性的证明。
- 每阶段运行相关 WLC Rust/生成 C、C11/C++20、Ztest、native_sim/QEMU、
  UDP 故障注入、FFI 和 Sanitizer；阶段完成前跑对应全量套件及远端 CI。
- 最终普通 RPC 无 now_ms、operation_id、token、inspect/release；普通业务
  不配置槽位字节数或处理借用字符串，自持结果脱离端点仍有效。
- 默认热路径零 allocator 调用、资源占用有界、停止后资源回到基线；连续使用
  不因默认一槽长 TTL 停顿。内存或 CPU 增长须有归因及对照，不以隐藏复制换取
  没有说明的体积膨胀。
- H1/H2/H3 分开记录；无实测不声明完成。若物理设备不可用，只列出具体待验项。

## 外部参考的用途

nanopb 的[有界字段静态表示](https://jpa.kapsi.fi/nanopb/docs/concepts.html#data-types)
支持“长度约束可以生成内嵌数组”的方向；不照搬其全部类型系统。
libcsp 的[事务接口](https://libcsp.github.io/libcsp/api/csp_h.html)展示了整合发送、
等待、复制结果和关闭的使用方式；Wirelink 的单 owner 与平台等待边界仍需自行实现。
