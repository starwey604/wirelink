# Codec 性能收敛：字段游标与预计算标签

日期：2026-09-09。本轮接续[编译期规划实验](codec-plan-performance-cn.md)，比较基线
是**上一轮已经优化过的 ABI 29**，不是最初的线性查找实现。业务 schema、公开 API、
owned 生命周期和线上格式均不变；不新增配置项，ABI 仍为 29。未提交、推送、合并、
发布或迁移产品 pin。

## 最终保留的改动

1. **预计算字段标签的字节与长度。** 字段编号和 wire type 在编译期已经确定，生成
   1–3 字节的规范标签。测长直接使用长度，编码直接写标签，规范化指纹使用同一份标签。
   不再在这些路径重复拼 key、计算其 varint 长度或编码 key。动态字段内容仍正常验证。
2. **解码使用局部顺序游标。** 若下一个字段恰好是预期字段，直接使用描述符；否则回到
   既有的线性/直接索引/二分查找。未知字段不推进游标，repeated 连续项可复用当前位置，
   每层嵌套解码有独立游标。游标只是提示，不是对输入有序性的要求。

在本次 x86-64 和 Arm EABI 构建中，标签数据占用描述符原有 padding：每字段仍为
**96 B / 64 B**。消息描述符也不再增大，没有新增持久 RAM、堆分配、锁或调用者存储。
标签写入只展开最多三个字节，不展开业务字段或整个数组。

公共 encode 仍先验证和测长，容量不足时不写输出；decode 的错误码、部分输出状态、
未知字段、重复字段、required、容量限制和 UTF-8 检查不变。指纹仍基于规范化内容，
**不是对收到的原始字节直接哈希**。

## 实验取舍

- 单独移除 `wlc_encode` 的 `inline` 未产生稳定收益，不保留这项改动。
- 只缓存标签长度的主机收益较小；连标签字节一起预计算后，普通编码改善明显。
- 另试过让连续编号显式绕过游标，希望减少逆序回退成本。但新增控制流在主机和 H7
  上均更慢，H7 连续 16–64 字段完整解码约退化 4.5%–5.2%；该候选已弃用。
- 不继续增加每架构策略、用户开关或消息展开。少字段阈值仍为 8；9–16 字段已加入
  正确性矩阵，但**没有逐个完成性能阈值扫描**，不声称找到了全平台最优阈值。

## 测量边界

复用[同一套 benchmark](../benchmarks/codec_plan/README.md)，不改变 workload v1。
主机 Linux x86-64、环境报告 6 个 CPU，GCC 16.2.1、Google Benchmark 1.9.5，Release
`-O3 -DNDEBUG`、无 LTO。用户控制背景负载后，**重新按严格串行顺序采集**，并将所有
主机进程固定在 CPU 1（`taskset -c 1`）。`lscpu` 显示 CPU 0/1 最高 4.5 GHz、其余
最高 3.3 GHz；固定相同核心避免迁移因素，但不禁用调频/ASLR，也不保证完全无背景干扰。

codec 108 组各 7 次、最短 0.05 s；完整 API 9 组各 7 次、最短 0.1 s，分别按
A/B/B/A 串行运行。所有计时完成后才连接 J-Link 做独立 H7 采集，再依次运行 CTest、
Zephyr 回归。**性能阶段不构建、不运行其他测试，也不同时进行主机计时和 RTT 采集。**
早期正确性 CTest 与 Zephyr 曾并行，但 smoke 耗时不用于性能结论；本页主机数据以
`converge-serial-*` 复测替换早期未固定核心的数据，不混合统计。

H7 为 STM32H723ZG / dm_mc02、550 MHz，Zephyr SDK 1.0.1 / GCC 14.3.0，`-O2`、
LTO、I/D cache 开启。沿用带编译器屏障的 DWT 计时、计时外 I-cache 失效、临时屏蔽
中断、独立字节 oracle。每次启动 225 组 × 5 样本。严格串行复测按 A/B/B/A 完成
四次启动：**4,500 样本、144,720 次计时内操作**。基线和候选各自两次启动的组中位数
差异最大约 **1.4% / 2.4%**。早期五次采集及弃用候选另存，不混入最终统计。

本轮 H7 主比较均为 LTO，不把上一轮无 LTO 数据冒充本轮复测。冷热、混合负载是
受控 codec CPU 测试，冷入口不是硬件 I-cache miss 计数，也不是 Willow 总 CPU 或通信 RTT。

## H7 结果

A 轮，热缓存、完整正序字段，每操作中位数，单位 µs；B 轮确认趋势。

| 操作 | 上一轮 → 本轮 | 时间减少 |
| --- | --- | --- |
| 稀疏 16 字段解码 | 8.255 → 7.203 | 12.7% |
| 稀疏 32 字段解码 | 16.849 → 14.237 | 15.5% |
| 稀疏 64 字段解码 | 34.701 → 28.244 | 18.6% |
| 连续 16 字段编码 | 2.890 → 2.497 | 13.6% |
| 连续 32 字段编码 | 5.741 → 5.002 | 12.9% |
| 连续 64 字段编码 | 11.228 → 9.771 | 13.0% |
| 稀疏 16 字段编码 | 3.386 → 2.763 | 18.4% |
| 稀疏 32 字段编码 | 6.575 → 5.253 | 20.1% |
| 稀疏 64 字段编码 | 12.846 → 10.271 | 20.0% |

连续 16–64 字段顺序解码约减少 0.8%–1.4%，不作为主要收益。
冷 I-cache 下，稀疏 16–64 字段顺序解码减少约 **10%–18%**，普通编码减少约
**10%–19%**。混合正序负载解码减少 **9.4%–9.6%**，编码减少 **13.6%–13.7%**，
测长减少 **26.7%–27.5%**。之前单数组专用路径不再改动。

| 整个 LTO 测试镜像 | 上一轮 | 本轮 | 增量 |
| --- | --- | --- | --- |
| FLASH | 62,124 B | 62,012 B | −112 B |
| RAM | 104,960 B | 104,960 B | 0 |

这不是 Willow 的剩余 FLASH：产品配对源码/pin 未迁移，不能据此承诺产品升级余量。
游标使用栈局部变量；检查本轮 LTO 反汇编，通用 `wlc_decode.part.0` 的保存寄存器与
局部区合计 **72 → 80 B，每层 +8 B**。这不是整个调用链的峰值栈测量；嵌套较深的
产品还需验证栈高水位，不能将链接 RAM 不变解读成栈开销也不变。

### 保留的代价

游标失配需要额外判断。H7 完整逆序的连续消息解码约 **+5%–6%**，稀疏消息约
**+3.6%–3.9%**；混合逆序解码约 **+4%**，高缺省混合解码约 **+1.1%–1.5%**。
float32[30] 专用解码虽源码未变，链接后的热缓存耗时约 **+4%**；128/64 元素的
两个数组解码约 +1% / 持平。这些不是全面加速，也不将它们掩盖为全部测量噪声。

保留当前方案的依据是 Wirelink 编码器本身按规范字段顺序发送，常见双端 WLC 场景
能命中游标，同时编码收益不依赖接收字段顺序。外部编码器若经常乱序，应单独测量。
协议仍完整接受合法乱序输入，不把性能偏好变成新的线上约束。

## 主机结果

两轮完整正序输入，相对上一轮：

- 连续 16 字段编码 **81.06 → 62.06 ns**、**83.70 → 62.36 ns**，减少 **23.4%–25.5%**；
  连续 8–64 字段编码整体约减少 **17%–26%**。
- 稀疏 16 字段解码 **118.90 → 72.40 ns**、**118.99 → 72.30 ns**，两轮均减少约 **39%**；
  32/64 字段约减少 **39% / 46%**。
- packed 编码大致持平。连续 16 字段逆序解码两轮约 **+8.0% / +5.5%**，属于回退成本，
  不宣称所有输入分布都提升。

另对最初的「编译期规划之前」冻结二进制补测两个历史退化项（仅这两组、7 次重复、
0.1 s、同一 CPU 1、A/B/B/A）：连续 16 字段编码 **74.82 → 62.22 ns**、
**75.15 → 62.20 ns**；稀疏 16 字段解码 **110.31 → 72.14 ns**、
**109.79 → 72.01 ns**。两个重点项也已优于最初基线；这项专项检查不冒充完整矩阵。

### 完整 API：不能沿用早期的小幅加速结论

12 服务、4 槽、reliable loopback 的复测中，0/32 B 单次 RPC 在 A 轮约 **+2.2%–2.5%**，
B 轮约 **−2.1%–2.8%**，方向反转，因此**不判定为稳定收益或稳定退化**。512/1024 B
RPC 在 ±1% 内；telemetry **1.979 → 1.983 µs**、**1.977 → 1.989 µs**（约 +0.2%/+0.6%），
也不宣称改善。此前未固定核心时「小 RPC 快约 2%」的结论不再作为最终结论。
端点仍为 **24,624 B**，arena 和协议时钟读取次数相同。codec 加速没有在该整条 API
负载中体现为同量级收益；本轮没有以 UDP smoke 的耗时当作两进程网络延迟。

## 正确性与验收

- WLC **127/127**，fmt/clippy 通过。公开 C/C++、owned、RPC、FFI 消费测试随全套运行。
- 新增冻结的线性解码 oracle（含独立嵌套递归），对 24 个连续/稀疏形状和混合消息做
  **102,400 组差分输入**，另测每个截断位置。包括乱序、缺省、未知、重复、畸形输入、
  repeated 交错与容量不足；比较状态码、失败后的完整对象及调用者数组。
- 标签测试覆盖编号 1/15/16/2047/2048/65535、四种 wire type、packed 与非 packed，
  比较标签字节、长度及规范化哈希。原有全编号查找和 packed 差分测试仍通过。
- codec/owned/RPC validation/shared scratch 的 ASan/UBSan **10/10**；主机 Release
  CTest **20/20**、Clang Sanitizer **17/17**；API benchmark CTest **12/12**（含 UDP smoke），
  codec benchmark CTest **2/2**。ABI 29 fixture 已重新生成。
- 性能阶段全部结束、退出 J-Link 后，按顺序重跑以上 CTest、WLC 和契约测试，全部通过。
  随后独立运行 Zephyr：unit_testing、native_sim、Cortex-M3、RISC-V32 共
  **34/34 配置、236/236 用例**通过，无警告。Clang Sanitizer 的 17 项不包含 Python bridge
  与独立 Release 扩展构建；这些消费路径由 Release 套件覆盖。

## 后续边界

这轮停止增加通用 codec 策略。下一个有价值的验收是配对迁移后的真实 Willow/FCI
消息分布、完整 RPC/telemetry CPU 和调度负载；先确认 codec 在总成本中的占比，再决定
是否值得专用化多字段固定数组、嵌套有界消息或继续调整稀疏阈值。迁移/发布另行进行。

最终材料位于本机 `build/performance-deps/`：

- `converge-serial-codec-{before,after}-{a,b}.json`：同核、完整 codec 矩阵。
- `converge-serial-api-{before,after}-{a,b}.json`：完整 API 矩阵；
  `converge-serial-recovery-{before,after}-{a,b}.json`：两个历史退化项的专项对照。
- `converge-serial-h7-{before,after}-{a,b}.log`：四次完整 H7 采集及相应 compare 日志。
- `converge-serial-*-tests.log`、`converge-serial-zephyr/`：独立正确性回归。
- `converge-serial-frozen-sha256.txt`、`converge-serial-affinity.log`、
  `converge-serial-jlink.log`：二进制、亲和性和烧录记录。
- `converge-serial-validation-summary.log`、`converge-serial-captures-sha256.txt`：
  完整矩阵/重复次数/上下文/工作量计数核对及原始采集哈希。
