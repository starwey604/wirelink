# WLC 编译期规划：字段查找与固定数组

后续已完成[字段游标与标签预计算收敛](codec-convergence-performance-cn.md)。本文保留
第一轮数据和当时的已知退化，当前实现与后续取舍请以续篇为准。

日期：2026-09-09。基线是上一轮已完成的 ABI 29（规范化指纹/验证复用）。本轮只改
生成 codec 的内部实现、测试与文档，**业务 schema、公开接口/布局、线上字节和 ABI 29
均不变**。未提交、推送、发布或合并，未迁移 libflorid/Ragtime 的源码或 pin。

## 本轮选择

| 消息形状 | 生成策略 | 边界 |
| --- | --- | --- |
| 不超过 8 个字段 | 继续线性查找 | 不为小消息生成分支树 |
| 更多字段且编号连续 | 编译器标记直接索引 | 不要求编号从 1 开始，越界返回未知字段 |
| 更多字段且编号稀疏 | 对已排序描述表二分查找 | 不分配另一份索引或大 jump table |
| 只有一个固定 packed 数组 | 专用 size/encode/decode 入口 | 固定前缀/长度/元素宽度，元素保留循环 |
| 其他消息 | 继续共用描述表引擎 | 不全面展开所有类型或嵌套子树 |

另外将每个字段的 wire type 提前计算，避免编码、测长和解码重复按类型判断。
它放入原有 padding：字段描述符在 H7 仍为 **64 B**、主机仍为 **96 B**。
消息描述符新增查找策略，H7 **8 → 12 B**、主机 **16 → 24 B**；均为生成 C 的私有
只读数据，不是业务结构或新增 RAM。未增加运行时分配、锁或业务配置。

固定数组包括 optional/required 的 fixed32/fixed64/float32/float64。只展开固定
4 字节标量的拼接表达式，**不展开 30/128 个元素**。公开编码仍在容量检查成功后才写；
解码保留未知字段、错误码优先顺序、重复字段、非规范 varint、required 和失败后状态。
普通 owned API 继续复用 codec，但其 value/view 转换成本不会因此自动消失。
嵌套的单数组子消息仍可能走通用递归入口，未声称任意有界消息都成为常量时间路径。

实现入口：`wlc/src/codegen.rs`、`packed_codegen.rs`、`packed_codec.c.in`。
阈值 8 是本轮策略，不是 API 承诺或所有处理器上的最优阈值。

## 测量方法

[新 benchmark 与复现命令](../benchmarks/codec_plan/README.md)独立于 core 构建。
包含 2/8/16/32/64 字段、连续/稀疏编号、正序/逆序/最后字段加未知字段，以及三个单数组
消息：float32[30]、required float32[128]、float64[64]。分别测 view-decode、view-encode、
encoded-size。编码 oracle 独立构造字节，不以待测编码器的结果验证自身。

主机为 Linux x86-64（环境报告 6 个 CPU）、GCC 16.2.1、Google Benchmark 1.9.5，
Release `-O3 -DNDEBUG`、无 LTO。冻结二进制后，108 组各 7 次、最短计时 0.03 s，
按 A/B/B/A 顺序串行运行；计时期间不编译或并行跑回归。CPU 和 wall time 分开保留。
CPU scaling 和 ASLR 仍开启，因此小幅差异不作为通用性能保证。

H7 是 STM32H723ZG / dm_mc02，550 MHz，Zephyr 4.4.99，SDK 1.0.1 / GCC 14.3.0，
`-O2`、I/D cache 开启。**主要比较两边都开启 LTO**，另建成对关闭 LTO 的诊断镜像。
核对最终 `.config`、实际 `-flto=auto` 和板上输出，而不只看 prj.conf。

每次启动 225 组 × 5 样本，分为热缓存、每操作前清空 I-cache、多种消息轮换三种模式。
前两种每样本 32 操作，混合模式 36 操作（12 种各三次）。DWT 对每次操作计时，加入
编译器内存屏障防止 LTO 跨计时点移动工作。临时屏蔽中断；清缓存、校验、RTT 和 sleep
在计时外，计时/调用开销保留在两边，不估算扣除。冷入口不是 cache-miss 硬件计数器，
混合矩阵也不是实际 Willow 工作集，不能当成产品总 CPU 或通信 RTT。

正式 LTO 两轮 A/B 配对加候选第三次启动，以及无 LTO 一轮配对，共七份完整采集、
**7,875 个样本、253,260 次计时内操作**。主比较中基线重复的各组中位数最大差异约
0.96%，候选前两次约 2.29%，第三次与 A 轮比较约 2.36%；百分比波动最大的包括极短的 size 路径。

## H7：LTO 开启后的结果

下表为 A 轮热缓存、完整正序字段，每操作中位数，单位 µs。B 轮确认相同趋势。

| 操作 | 基线 → 本轮 | CPU 时间减少 |
| --- | --- | --- |
| 连续 16 字段解码 | 7.527 → 6.288 | 16.5% |
| 连续 32 字段解码 | 17.570 → 12.659 | 28.0% |
| 连续 64 字段解码 | 44.622 → 25.470 | 42.9% |
| 稀疏 16 字段解码 | 8.475 → 8.271 | 2.4% |
| 稀疏 32 字段解码 | 19.326 → 16.848 | 12.8% |
| 稀疏 64 字段解码 | 47.771 → 34.693 | 27.4% |
| float32[30] 编码 | 1.493 → 0.394 | 73.6% |
| float32[30] 解码 | 1.531 → 1.147 | 25.1% |
| float32[128] 编码 | 5.272 → 1.025 | 80.6% |
| float32[128] 解码 | 4.707 → 3.411 | 27.5% |
| float64[64] 编码 | 4.254 → 1.949 | 54.2% |
| float64[64] 解码 | 5.832 → 4.887 | 16.2% |

普通多字段标量编码也受益于预计算 wire type：B 轮完整 8–64 字段约减少 10%–15%。
单数组的 size 路径直接使用已知编码长度，不再逐层测长；含计时/调用开销约减少 60%–64%。

冷 I-cache 下，连续 16–64 字段解码减少约 **14.7%–41.7%**；三个数组的编码减少
**61.2%–80.7%**、解码减少 **18.1%–24.3%**。新增代码没有在这些冷入口用例里吞掉收益。
两轮混合负载（含三种字段顺序/缺省分布）解码减少 **16.4%–26.1%**，编码减少
**22.8%–30.9%**。这比仅展示连续调用同一个小函数更有参考价值，但仍非产品工作集。

保留已知小路径代价：热缓存下 2 字段完整消息解码从 **0.988 → 1.073 µs**，约 +8.7%。
8 字段完整消息约持平。根据本轮约定，不继续追逐独立小消息 decode 的布局差异。

| 整个 H7 测试镜像 | 基线 | 本轮 | 增量 |
| --- | --- | --- | --- |
| LTO 开启：FLASH | 60,740 B | 62,124 B | +1,384 B |
| LTO 开启：RAM | 104,960 B | 104,960 B | 0 |
| LTO 关闭：FLASH | 66,312 B | 67,232 B | +920 B |
| LTO 关闭：RAM | 105,088 B | 105,088 B | 0 |

关闭 LTO 的补充对照也确认收益：完整连续 16–64 字段解码减少 17.8%–42.7%，
三个数组编码减少 59.4%–79.7%，解码减少 13.2%–24.3%。不能把 LTO 关闭时的增量
直接套到开启后的产品。**上述为本轮测试镜像的实际链接占用，不是 Willow 剩余 FLASH**；
产品未迁移，不能用此 app 的空闲空间承诺完整 Willow 的升级余量。

## 主机结果与限制

两轮完整连续 16/32/64 字段解码减少约 **33%–37% / 42%–50% / 63%–65%**。
但不能宣称全平台全面加速：16 字段稀疏解码两轮分别 **+8.8% / +11.8%**；
连续 16 字段编码 **+11.8% / +17.3%**。部分更大编码组的波动也很明显。
主机 packed 编码原本已被 GCC 较好优化，约持平，没有 H7 同量级收益；float64[64]
解码也未体现稳定改善。这些差异保留为阈值/代码布局调优目标，不从报告中删除。

现有 12 服务、4 槽、reliable loopback API benchmark 另做两轮对照：0/32 B 的 RPC
每调用 CPU 减少约 **1.5%–3.0%**，四调用批次约 **2.0%–2.6%**；512/1024 B 差异小，
不宣称稳定提升。完整 Telemetry 的两轮为 **2.013 → 1.994 µs**、
**2.022 → 1.983 µs**（约 0.9%–1.9%）。端点仍为 **24,624 B**，公共布局未增大。
codec 百分比不能当作整条通信链的百分比；本轮没有正式测两进程 UDP 网络延迟。

## 正确性与过程记录

- WLC **125/125**，fmt/clippy 通过；新契约与 owned、RPC 验证复用、shared scratch
  合计 **8/8** 在 ASan/UBSan 下通过。公开 C11/C++ 和 FFI 消费测试随全套运行。
- 对少字段、连续字段和稀疏字段各遍历完整 0–65535 编号空间，比对线性查找 oracle；
  schema 刻意逆序声明，覆盖非 1 起始编号和未知编号。
- 对 optional/required、32/64 位数组进行 **12,288 组差分输入**，包括变异、随机字节、
  重复字段与未知字段；另覆盖每个截断位置、每个短容量、NULL、缺 required，比较
  字节、错误码、输出长度及失败后的完整对象状态。未取消外部输入检查。
- ABI 29 fixture 已重新生成；Zephyr unit 加 protocol/application-runtime/bulk
  integration **34/34 配置、236/236 用例**，覆盖 unit_testing、native_sim、Cortex-M3
  和 RISC-V32 QEMU。既有 packed/frozen-vector 用例使用新实现。
- 主机 Release CTest **20/20**、Clang ASan/UBSan **17/17**（排除 Python bridge 和独立
  Release 扩展构建）；API benchmark CTest **12/12**，含真实 UDP smoke。
  新 benchmark CTest **2/2**，其中解析器 **4/4**；smoke 时间不用于判断性能。

首版逐字节拼接的 float32 专用解码保留了内层循环，板上变慢 10%–27%；已弃用，

## 剩余值得推进的点

1. 调优稀疏 9–16 字段阈值，比较有序字段游标、紧凑索引和分支策略；本轮未逐个测
   9–15 字段，也未生成每消息 switch 树，不假称已穷尽所有策略。
2. 解释/收敛主机通用编码退化，继续同时看 H7 LTO 下的 FLASH 和冷热工作集，不按单一
   主机分数决定展开范围。
3. 对实际高频有界消息按 profile 取样；若继续专用化多字段/嵌套结构，必须保留通用 oracle
   与布局门限。owned 转换、动态 varint 长度仍需单独计量。
4. 产品配对迁移后再测完整 Willow CPU、总 FLASH 与调度影响；本轮不是产品发布验收。

最终板上保留 **LTO 开启的 codec CPU benchmark，不是 Willow**；采集和探针均已退出。
