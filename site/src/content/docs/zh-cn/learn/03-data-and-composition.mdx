在嵌入式 C 开发中，一旦协议出现变长字符串（如设备名称、固件版本号）或二进制块（如传感器原始载荷），通常要解决两个问题：如何避免动态申请 `malloc/free`，以及如何在接收回调返回后安全保留解码结果。

本课结合双进程示例 [`examples/02_device_info/`](https://github.com/starwey604/wirelink/tree/main/examples/02_device_info) 与多模块协议 [`examples/04_composed_services/`](https://github.com/starwey604/wirelink/tree/main/examples/04_composed_services)，介绍 Wirelink 的数据建模方式与回调生命周期规则。

## 第一步：用 `string<N>` 定义有界字符串

节点使用的消息需要具备编译期确定的最大字节长度，因此字符串和字节数组通过 `<N>` 指定上限（如 `string<31>`、`bytes<64>`）。编译器会将它们的存储直接内联在生成的 C 结构体中，不引入任何堆指针。

对比 [`examples/02_device_info/device_info.wl`](https://github.com/starwey604/wirelink/blob/main/examples/02_device_info/device_info.wl) 与生成的 C11 结构体：

<Tabs>
  <TabItem label="1. 协议定义 (device_info.wl)">
    {/* [docs:device_info_schema] */}
    ```wl
    version 1;

    message InfoRequest @id(30) {}

    message InfoResponse @id(31) {
      string<31> name @id(1);
      string<15> firmware @id(2);
      uint32 query_count @id(3);
    }

    rpc GetInfo(InfoRequest) -> InfoResponse;
    node info_client { call GetInfo; }
    node info_server { serve GetInfo; }
    ```
    {/* [/docs:device_info_schema] */}
  </TabItem>

  <TabItem label="2. 生成的 C11 结构体与安全 Setter">
    生成的 `info_response_t` 不含外部指针，字符串字节数组直接内联在结构体内部：

    ```c
    struct info_response {
      struct {
        size_t length;
        char data[32]; /* string<31> 分配 31 + 1 字节，解码后末尾自动补 '\0' */
      } name;
      struct {
        size_t length;
        char data[16]; /* string<15> 分配 15 + 1 字节 */
      } firmware;
      uint32_t query_count;
    };

    /* 生成的辅助 setter：校验长度不超过上限、复制内容并补 '\0'，超长返回 false */
    bool info_response_set_name(info_response_t *msg, const char *value);
    bool info_response_set_firmware(info_response_t *msg, const char *value);
    ```
  </TabItem>
</Tabs>

### 常用数据类型速览

除整数与 `string<N>` 外，`.wl` 还支持以下常用类型（完整列表见[.wl 协议语法手册](/wirelink/zh-cn/concepts/schema-language/)）：

| 数据类型 | `.wl` 写法 | 生成的 C11 成员 |
| :--- | :--- | :--- |
| **有界 UTF-8 字符串** | `string<31> name @id(1);` | `struct { size_t length; char data[32]; }`（线缆只传实际 `length` 字节，解码后补 `'\0'`） |
| **有界原始字节块** | `bytes<64> payload @id(2);` | `struct { size_t length; uint8_t data[64]; }`（可放任意二进制载荷） |
| **定长紧凑数组** | `packed float32 accel[3] @id(3);` | `float accel[3];` |
| **枚举类型** | `enum Mode @id(1) { IDLE = 0; RUN = 1; }` | 强类型 C `enum`，解码自动拒绝未定义枚举值 |
| **可选字段** | `optional int32 temp @id(4);` | `bool has_temp;` + `int32_t temp;`（未传时 `has_temp` 为 `false`，便于协议向后兼容） |

## 第二步：服务端写入字符串与客户端按值拷贝

由于 `info_response_t` 中的字符串是内联定长数组而非外部指针，在接收回调中直接执行结构体赋值 **`saved = *response;`** 即可完整深拷贝所有字段（包含全部字符串内容）。

<Tabs>
  <TabItem label="1. 服务端填写响应 (server.c)">
    在 [`examples/02_device_info/server.c`](https://github.com/starwey604/wirelink/blob/main/examples/02_device_info/server.c) 中，服务端通过 `self->node.user` 取出上下文计数并填写响应（这里展示了允许内嵌 `'\0'` 的定长 UTF-8 写法；普通 C 字符串也可直接调用 `info_response_set_name`）：

    {/* [docs:device_info_server] */}
    ```c
    int32_t info_server_on_get_info(info_server_node_t *self, const info_request_t *request, info_response_t *response) {
      (void)request;
      unsigned *queries = self->node.user;
      response->name.length = 11; memcpy(response->name.data, "workbench\0x", 11);
      response->firmware.length = 6; memcpy(response->firmware.data, "0.0.99", 6);
      response->query_count = ++*queries;
      return 0;
    }
    ```
    {/* [/docs:device_info_server] */}
  </TabItem>

  <TabItem label="2. 客户端回调按值拷贝 (client.c)">
    在 [`examples/02_device_info/client.c`](https://github.com/starwey604/wirelink/blob/main/examples/02_device_info/client.c) 中，`done` 回调将 `*response` 整体拷贝到静态变量 `saved`，而不是保存 `response` 指针：

    {/* [docs:device_info_done] */}
    ```c
    static void done(info_client_node_t *self, wl_rpc_result_t outcome, const info_response_t *response) {
      (void)self;
      result = outcome;
      if (response != NULL) saved = *response;
      ++completed;
    }
    ```
    {/* [/docs:device_info_done] */}
  </TabItem>

  <TabItem label="3. 客户端发起调用 (client.c)">
    客户端发出空请求 `InfoRequest` 并推进主循环直到回调完成；即使随后关闭节点，先前拷贝到 `saved` 中的字符串与 `query_count` 依然完好可用：

    {/* [docs:device_info_client] */}
    ```c
    static wl_err_t read_device_info(info_client_node_t *client) {
      const wl_clock_t clock = example_clock();
      wl_err_t error = info_client_call_get_info(client, &(info_request_t){0}, done);
      while (error == WL_OK && example_running() && !completed)
        error = wl_node_poll(&client->node, clock, 100U);
      return completed || error != WL_OK ? error : WL_ERR_CANCELLED;
    }
    ```
    {/* [/docs:device_info_client] */}
  </TabItem>
</Tabs>

<Aside type="caution" title="回调中的指针生命周期规则">
- 无论是单向消息的 `const <msg>_t *message`，还是 RPC 的 `const <resp>_t *response`，指针所指向的内部解码缓冲区**仅在当前回调函数返回前有效**。
- **不要保存指针**（如 `cached_ptr = response;` 或 `cached_str = response->name.data;`）。
- **应按值拷贝**（如 `saved = *response;`），所有内联字符串和字节数组会随结构体一并安全复制。
</Aside>

## 第四步：用 `import` 将多模块组合到同一个节点

当设备同时包含多个子系统（如机械臂控制、传感器遥测、固件升级）时，不必把所有消息塞进同一个 `.wl` 文件。可以在各子文件中分别定义各自的 `message` 与 `rpc`，再在顶层产品文件中用 `import` 组合进一个或多个 `node`。

查看 [`examples/04_composed_services/product.wl`](https://github.com/starwey604/wirelink/blob/main/examples/04_composed_services/product.wl)：

{/* [docs:composed_product_schema] */}
```wl
version 1;
import "arm.wl";
import "upgrade.wl";

node product {
  send Telemetry; recv Telemetry;
  send BulkCommand; recv BulkCommand;
  send BulkStatus; recv BulkStatus;
  call Query; serve Query;
  call Reboot; serve Reboot;
}
```
{/* [/docs:composed_product_schema] */}

使用 CMake 的 `wirelink_wlc_generate` 时，构建系统会自动调用 `wlc dependencies` 追踪所有被 `import` 的文件——只要任意子文件修改，下次构建都会自动重新生成 C 代码。

<Challenge
  title="检查理解：为什么 string<31> 可以用 saved = *response 安全跨回调保存？"
  prompt="在 C 语言中，如果结构体里存的是 const char *name，直接执行 saved = *response 通常会导致悬空指针；为什么 Wirelink 生成的 info_response_t 可以直接按值赋值？"
>
  因为 Wirelink 为 `string<31>` 生成的成员不是 `const char *` 指针，而是直接内嵌在结构体内部的定长数组 `char data[32]` 和长度字段 `size_t length`。执行 `saved = *response;` 时，C 编译器会按值将数组里的全部字节一起拷贝到目标结构体，不依赖任何临时缓冲或堆内存。
</Challenge>
