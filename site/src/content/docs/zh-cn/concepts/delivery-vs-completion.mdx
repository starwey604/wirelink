一次远程调用的请求可能已经可靠送达，但设备还没执行，或者明确拒绝。把这两种结果混为一谈，会写出错误的重试逻辑：要么把业务拒绝当成通信故障反复重发，要么在链路还没送达时就以为操作已经完成。

## 一次调用的四个阶段

1. 请求越过链路。
2. 服务端 handler 接受或拒绝操作。
3. 响应或拒绝信息返回客户端。
4. 客户端得到 RPC 结果。

可靠投递负责第 1、3 步的链路工作。只有业务处理和回复完成后，客户端才知道 RPC 结果。

## 链路确认证明什么

链路 ACK 或 `WL_EVT_TX_SUCCESS` 只说明可靠消息进入了 peer 的稳定 event storage。它不表示 handler 运行、不表示业务成功，也不表示 response 已经返回。规范性描述见 [Wirelink 协议规范](https://github.com/starwey604/wirelink/blob/main/docs/protocol-cn.md)。

## RPC 业务完成的几种终态

`endpoint_<service>_async()` 返回 `WL_OK` 只表示本地 endpoint 接受了请求快照。真正的结果稍后通过 `wl_rpc_completion_t` 报告：

- `WL_RPC_SUCCESS`：业务成功，此时才可以读取 response。
- `WL_RPC_REJECTED`：业务拒绝，状态保存在 `result.rejection`。
- 超时、取消和通信失败是另外几种彼此独立的终态。

托管 RPC 在业务编码前加上固定的 20 字节元数据，其中包含非零调用编号、业务状态和原客户端 session。请求状态为零；成功响应状态为零，后接业务响应；拒绝响应状态非零，且不携带业务响应体，即使响应 schema 有必填字段也不用伪造值。

## 为什么必须分开

链路可靠和业务失败是正常组合。服务端 handler 检测到溢出时可以返回非零业务状态：链路和 RPC 匹配都成功，业务仍然被拒绝。反过来，链路重传也不会让应用层重复执行同一次调用：托管 RPC 在配置的会话、缓存和过期范围内抑制重复通信请求并重放响应。但相同参数发起的新调用会再次执行，调用关联不等于业务幂等。

取消和超时只停止本地等待，不撤销远端已经发生的副作用。需要跨重试或持久幂等时，应显式设计业务键和状态机。

## 边界

- 链路 ACK 不是业务确认。
- 业务拒绝既不是链路失败，也不是超时。
- 一次调用已经在远端执行，不代表客户端一定拿到结果；响应可能在返回途中丢失。

## 常见误解

- 「`add_async()` 返回 `WL_OK` 就是成功了。」——它只说明本地接受了快照，最终结果要看完成回调。
- 「超时说明远端没有执行。」——超时只结束本地等待，远端可能已经产生副作用。
